## Architecture: one code path

The task pane and any Copilot skill action insert through the **same** headless service —
`src/actions/citationService.ts` — so there is no duplicated insert logic:

```
caller (pane form │ Copilot LLM │ jurisd skill/MCP)
        → CitationInsertRequest (this contract)
        → citationService.insertCitation()
        → engine.getFormattedPreview()  (pure AGLC4 formatting)
        → footnoteManager.insertCitationFootnote()  (native Word footnote)
        → citationRefresher.refreshAllCitationsNow()  (ibid/short-ref/renumber)
```

Obiter's engine stays the **authority for AGLC4 formatting**; the caller only supplies structured
fields. This is what keeps Obiter essential rather than trusting an LLM to format.

## Contract version

`CITATION_REQUEST_CONTRACT_VERSION` (see `src/actions/citationRequest.ts`) — bump on any breaking
change to the request shape. Read the live contract at runtime via
`getCitationInsertContract()` (`src/actions/actionCatalogue.ts`), which returns `{ contractVersion,
actions, sourceTypeSchema }`.

## CitationInsertRequest

| Field | Type | Notes |
|---|---|---|
| `sourceType` | string | AGLC4 source type, e.g. `case.reported`, `legislation.statute` |
| `data` | object | Source fields keyed per source type (see per-source schema below) |
| `shortTitle` | string? | Used for subsequent references |
| `signal` | string? | Introductory signal (Rule 1.3): `See`, `Cf`, … |
| `commentaryBefore` | string? | Discursive text before the citation in the footnote |
| `commentaryAfter` | string? | Discursive text after the citation |
| `overrideText` | string? | Verbatim footnote text; bypasses the engine |
| `aglcVersion` | `"4"\|"5"`? | Defaults to the document's active standard |
| `appendToFootnoteIndex` | number? | Append to an existing footnote (Rule 1.1.3) |

**Per-source-type fields** (which `data` keys are required/optional for each `sourceType`, with rule
numbers and templates) are machine-readable via `exportRuleReference()` / the `sourceTypeSchema` of
`getCitationInsertContract()`. A caller (Copilot LLM or jurisd) should read that schema to build a
valid `data` object.

## Actions (`OBITER_ACTIONS`)

| Action | Effect | Input | Description |
|---|---|---|---|
| `insertCitation` | mutation | `CitationInsertRequest` | Format + insert as a native Word footnote |
| `formatCitation` | pure | `CitationInsertRequest` | Return AGLC4 text without inserting |
| `updateCitation` | mutation | `{ citationId, request }` | Re-format + update all occurrences |
| `deleteCitation` | mutation | `{ citationId, footnoteIndex }` | Remove one occurrence |
| `refreshFootnotes` | mutation | (none) | Fix ibid/short-refs, renumber, normalise |

## Example: a jurisd skill (or Copilot) inserting a case

```jsonc
// Action: insertCitation
{
  "sourceType": "case.reported",
  "data": {
    "party1": "Mabo",
    "party2": "Queensland (No 2)",
    "year": "1992",
    "volume": "175",
    "reporter": "CLR",
    "startingPage": "1"
  },
  "shortTitle": "Mabo"
}
// → Obiter formats "Mabo v Queensland (No 2) (1992) 175 CLR 1" and inserts a native footnote.
```

## Cross-vendor reach (Claude for Word, Cursor, other GenAI tools)

The Copilot **add-in-as-skill** bridge (COPILOT-005) is **Microsoft-specific** — only Microsoft 365
Copilot can invoke an add-in's in-document operations, because Microsoft controls both ends. Other
GenAI Word add-ins (e.g. **Claude for Word**) **cannot** use it, and Office does not let one add-in
call another add-in's code (each runs in an isolated runtime; they share only the document). So a
third-party tool cannot trigger Obiter's *managed* insertion.

What third-party tools **can** do is consume Obiter over **MCP**: Obiter's engine is pure TypeScript
(no Office.js), so `formatCitation` / `validate` / the per-source-type schema can run as a
**standalone MCP server** any MCP-capable tool calls to get correct AGLC4 **text**, which the tool
then inserts itself (via its own tracked-changes edit).

- **Formatting/validation for any tool → yes** (an additive engine MCP server; GPLv3-clean network
  boundary — invoke, not embed).
- **Managed native-footnote insertion → Copilot-bridge-only.** A citation another tool inserts is
  *its* footnote — not Obiter-managed (no XML-part store binding, so Obiter's ibid/short-ref/renumber
  logic will not track or refresh it). Only Obiter's own add-in or the Copilot bridge can create a
  managed footnote, because that needs the Word Office-JS runtime.

Potential follow-up story: **an Obiter engine MCP server** (`format`/`validate`) wrapping the pure
engine, serving any GenAI tool — reuses this same contract.

## Licensing boundary (jurisd interop)

Obiter is **GPLv3**; jurisd is **Apache-2.0**. A jurisd skill/MCP must **invoke** these actions across
the skill/process boundary — **not embed** Obiter's engine code — so jurisd stays Apache-2.0 and
Obiter stays GPLv3 (GPLv3, unlike AGPL, does not cross a process/network invocation). See
DECISION-011 point 8.

### COPILOT-003 — Shared runtime (manifest) — **BUILT (staged in `manifest.skill.xml`)**

The Copilot-skill mechanism and cross-runtime invocation need a **shared runtime**.
`manifest.skill.xml` (a validated variant, not the production manifest) adds it inside the
VersionOverrides:

```xml
<Requirements>
  <bt:Sets DefaultMinVersion="1.1">
    <bt:Set Name="SharedRuntime" MinVersion="1.1"/>
  </bt:Sets>
</Requirements>
<!-- and, as the first child of <Host>: -->
<Runtimes>
  <Runtime resid="Taskpane.Url" lifetime="long"/>
</Runtimes>
<!-- FunctionFile now targets the shared Taskpane page -->
```

This removes the `commands.ts` static-imports-only constraint, so commands can call the shared
`citationService` instead of inlining logic. **Sideload-time wiring step:** migrate the `commands.ts`
handlers into the shared runtime page and **verify existing ribbon commands + task pane still work**.
The webpack change (point commands at the shared page) is intentionally **not** applied to the
production build.

### COPILOT-005 — Register the add-in as a Copilot skill — **BUILT**

Per Microsoft's **"Combine Copilot Agents with Office Add-ins" (preview)**, the add-in is declared as
a skill exposing `OBITER_ACTIONS`. `buildCopilotSkillManifest()` (`src/actions/skillManifest.ts`)
generates the declaration from `OBITER_ACTIONS` + `getCitationInsertContract()`; `npm run export-skill`
emits `docs/obiter-copilot-skill.json`. The exact preview agent-manifest schema is not in the
validated add-in XSD, so `manifest.skill.xml` references the generated declaration rather than inlining
an unvalidated element — bind it per
<https://learn.microsoft.com/office/dev/add-ins/design/agent-and-add-in-overview> when applying the
preview.

### COPILOT-006 — Structured results + review UX — **BUILT (direct insert)**

Actions return typed results (`InsertResult`). The review model is resolved to **direct insert**
(`reviewMode: "direct"` in the skill manifest): the skill inserts the native footnote and returns the
structured result; the user reviews via Copilot's confirmation and Word's track changes. No task-pane
prefill (driving the pane from a skill action is not a guaranteed Office capability).

### COPILOT-007 — No-BYOK parse/classify via Copilot — **BUILT**

"Help me choose" (classify) and "Paste Citation" (parse) are **pure LLM tasks** — Copilot's own LLM
does them, then calls `insertCitation`/`formatCitation` with the structured request. The AGLC4-tuned
prompts are exported as shared constants (`CLASSIFY_SOURCE_SYSTEM_PROMPT` in `llm/classifySource.ts`,
`PARSE_CITATION_SYSTEM_PROMPT` in `llm/parseCitation.ts`) and `buildAgentInstructions()`
(`src/actions/agentInstructions.ts`) embeds them **verbatim** into the agent instructions — one source
of truth, so the Copilot path cannot drift from the BYOK path. **No API key** on the Copilot path;
**BYOK unchanged** for free/non-Copilot users. Needs no jurisd — the smallest, self-contained slice.
